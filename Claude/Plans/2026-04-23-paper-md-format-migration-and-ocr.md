# `.paper.md` Format Migration + OCR Integration

**Date:** 2026-04-23
**Research:** [`Claude/Research/2026-04-23-paper-file-searchability-and-ocr-approaches.md`](../Research/2026-04-23-paper-file-searchability-and-ocr-approaches.md)
**Status:** Planning. Awaiting approval before implementation.

## Goals

1. **Full-text search** of handwritten notes works through Obsidian's native search — no plugin-specific index.
2. **Metadata participates** in the standard Obsidian graph: tags, frontmatter properties, backlinks, Bases, Dataview all work on paper notes.
3. **OCR runs incrementally and cheaply** — only re-process lines whose strokes changed.
4. **Privacy opt-in** — no strokes leave the device unless the user configures a backend and provides an API key.
5. **One-time migration** of the user's existing `.paper` files; no backwards-compat shims to carry forever.

## Non-Goals

- Supporting multiple simultaneous users on the same file.
- Live collaborative editing.
- Offline/local OCR that matches cloud quality (acknowledged limitation, not a goal).
- Migrating away from MyScript if it disappears — we'll cross that bridge if it happens.
- Real-time OCR as the user writes. Debounced after idle or on save is sufficient.

## File Format Specification

### On-disk layout (v4)

A `.paper.md` file is a valid markdown file with three structured sections:

1. **YAML frontmatter** — required, contains `paper-version`, timestamps, and any user-added tags/properties.
2. **`# Transcript` heading + plaintext body** — optional, regenerated by OCR. When OCR is disabled, this is empty (but the heading exists so edits don't clobber anything if OCR is later enabled). Each page gets its own H2 like `## Page 1`.
3. **Fenced code blocks**:
   - `` ```paper `` — required, contains deflate+base64 of the scene JSON (same JSON structure we write today, minus `meta.created`/`modified` which move to frontmatter).
   - `` ```paper-ocr `` — optional, contains deflate+base64 of the structured OCR result (per-line bboxes, confidences, stroke↔word mapping). Omitted when OCR hasn't run.

Any other markdown content between these sections is user-authored and preserved verbatim on round-trip. The Paper editor doesn't render user markdown — it's invisible from the canvas UI, only visible in the markdown view.

### Frontmatter schema

```yaml
---
paper-version: 4
paper-created: 2026-04-23T14:00:00Z
paper-modified: 2026-04-23T14:05:32Z
paper-default-view: paper        # "paper" | "markdown", controls which view opens by default
paper-ocr:
  backend: myscript              # "myscript" | "handwriting-ocr" | null
  last-run: 2026-04-23T14:05:32Z
  doc-hash: a3f9…                # hash of the scene JSON at time of last OCR
tags: []
---
```

- `paper-version` is checked on load; mismatch triggers migration prompt (we only ever migrate forward).
- `paper-default-view` is the mechanism Excalidraw uses for per-file view routing. User toggles it per file via command.
- `paper-ocr` is a namespaced object, so user-added frontmatter at the top level doesn't collide.

### Scene JSON (inside `` ```paper ``)

Same `PaperDocument` structure as today's `.paper` files (pages, styles, strokes, etc.), with these adjustments:
- Drop `meta.created`/`meta.modified` (moved to frontmatter).
- Keep `meta.appVersion` for debugging.
- Keep the existing delta-encoded point format. No reason to change it.
- Apply deflate+base64 unconditionally (no 10KB threshold). Markdown + raw JSON gets ugly on `git diff` and large inline JSON slows down the markdown parser.

### OCR JSON (inside `` ```paper-ocr ``)

```json
{
  "v": 1,
  "backend": "myscript",
  "pages": [
    {
      "pageIndex": 0,
      "lines": [
        {
          "id": "L-0-3",
          "text": "first line of handwriting",
          "bbox": [x, y, w, h],
          "confidence": 0.94,
          "strokeIds": ["s-a1b2", "s-c3d4"],
          "words": [
            { "text": "first", "bbox": [...], "strokeIds": [...] }
          ]
        }
      ]
    }
  ]
}
```

- `id` is stable per line — we reuse line IDs across re-OCR runs to enable incremental updates.
- `strokeIds` at both line and word level — enables click-to-select-strokes and dirty tracking.
- Stored deflate+base64 to keep markdown clean and diff-friendly.

## Key Design Decisions

### 1. Extension: `.paper.md`

`.paper.md` (not a bare `.md` with a frontmatter flag). Reasons:
- Obvious in the file explorer that it's a paper note.
- Matches Excalidraw's precedent — users already understand the pattern.
- Lets us write a simple filter for `isPaperFile(file: TFile)`.
- Under the hood it's still a `.md` so Obsidian indexes it natively.

### 2. Routing `.paper.md` files to the Paper editor

The hard part. Obsidian opens `.md` in the markdown editor by default. Plan:

- Register a view type `VIEW_TYPE_PAPER` (we already have this).
- On `app.workspace.on('file-open', file)`, check:
  1. File path ends in `.paper.md`.
  2. `paper-default-view` in frontmatter is `"paper"` (default if missing).
  3. The leaf currently showing this file is a markdown view.
- If all three, call `leaf.setViewState({ type: VIEW_TYPE_PAPER, state: { file: file.path } })` to switch it.
- Register a command "Toggle Paper/Markdown view" that flips `paper-default-view` in frontmatter and re-opens.
- Register a command "Create new paper note" that writes a seed `.paper.md` and opens it directly in the Paper view.

This is essentially the Excalidraw model and it works reliably there.

### 3. Transcript placement & visibility

- **Paper editor:** the transcript is not rendered in the canvas surface. It's metadata from the editor's point of view. Optional side panel (phase 4) can show the current page's transcript for review.
- **Markdown editor:** the transcript renders normally as markdown. Hover previews, search snippets, Dataview all see it.
- **Regeneration:** when OCR runs, we overwrite the `# Transcript` section wholesale. User edits within the transcript get clobbered — that's acceptable because the transcript is derived data, but we'll document the behavior and add a "this is auto-generated, edits may be lost" comment under the heading.

### 4. Compression: always deflate+base64

Current behavior: compress at 10KB. New behavior: always compress in markdown context. Keeps line-diffs clean and keeps the markdown parser fast.

### 5. OCR trigger policy

- **Off by default.** No API call happens until user enters an API key in settings.
- **On save, debounced.** Default debounce: 30 seconds of no-stroke-edits. Runs only on dirty lines.
- **On demand via command:** "Recognize handwriting on current page" and "Recognize handwriting on entire document."
- **Progress UI:** a notice with "Recognizing page N of M" and inline spinner in the status bar.
- **Error UI:** a notice with error reason, link to docs. No retries on HTTP errors; users can re-run manually.

### 6. Stroke ↔ line clustering

To run incremental OCR, we need stable line groupings. Algorithm:
1. Project each stroke's bbox centroid onto the page Y-axis.
2. Cluster by Y-distance with a threshold proportional to median stroke height.
3. Order clusters top-to-bottom, assign stable line IDs (`L-<page>-<clusterIndex>`).
4. Cluster re-runs on every stroke add/remove, but a stroke's line assignment stays stable as long as the cluster it belongs to remains intact.
5. If a cluster splits or merges due to edits, mark affected clusters dirty.

Fallback for weird cases (strokes that span lines, very sloppy writing): just treat the whole page as one dirty region and re-OCR the page. Cost is still low.

### 7. OCR backend abstraction

```typescript
interface OcrBackend {
  id: "myscript" | "handwriting-ocr";
  recognizePage(input: OcrPageInput): Promise<OcrPageResult>;
  isConfigured(): boolean;
}

interface OcrPageInput {
  page: Page;
  strokes: Stroke[];          // pre-filtered to the lines we want
  lines: LineRegion[];        // optional hint
  pageBitmap?: ImageData;     // image-based backends use this
}
```

Both backends implement this. `recognizePage` may choose to send strokes or rasterize to an image depending on the backend — that's an implementation detail hidden from the pipeline.

### 8. Cost safety valve

- Settings option: `maxOcrCallsPerMonth` with a sensible default (e.g., 5000 — enough for a heavy user, below MyScript's hobbyist tier).
- Counter persisted in plugin data, reset monthly.
- When hit, OCR pauses and surfaces a notice. User can raise the cap in settings.

### 9. Migration strategy

One-time command, run manually by the user. Not automatic on plugin load. Steps:

1. Scan vault for `*.paper` files.
2. For each:
   - Read + deserialize with the v3 deserializer (keep v3 deserializer in the repo; it's small).
   - Emit `<same-basename>.paper.md` with the v4 format (frontmatter, empty transcript, compressed code block).
   - Verify the new file deserializes correctly round-trip.
   - If verification passes, delete the original `.paper`.
   - If verification fails, log and skip. User inspects and decides.
3. Scan markdown files for `![[foo.paper]]` embeds; rewrite to `![[foo.paper.md]]` (Obsidian resolves extensions either way, but the explicit form is clearer).
4. Report summary: N migrated, M failed, paths of failures.

Dry-run mode: runs steps 1–3 in memory, writes a report to `Claude/` or shows it in a modal, makes no file changes. Ship this first; run for real after dry-run looks clean.

## Implementation Phases

Each phase ends with `yarn build && yarn test && yarn build:copy` passing. Commit between phases. Features flagged or ship incomplete — only Phase 1 is load-bearing for everything after.

### Phase 1 — Format skeleton + round-trip (1–2 days)

- [ ] Define TypeScript types for v4 format: `PaperMdFrontmatter`, `OcrResult`, updated `PaperDocument` (minus timestamps).
- [ ] Write `PaperMdSerializer.ts` (new) that:
   - Serializes `PaperDocument` + OCR result → markdown string with frontmatter + transcript + both code blocks.
   - Deserializes markdown string → `PaperDocument` + optional `OcrResult`.
   - Preserves unrecognized markdown content between known sections.
- [ ] Keep `Serializer.ts` (v3) as `SerializerV3.ts` for migration use only; unused in normal flow.
- [ ] Add unit tests for round-trip with and without OCR, with and without user-added markdown.
- [ ] Decide file storage: the `.paper.md` file has two code blocks that can be big. Verify markdown parser handles 100KB code blocks without choking on mobile. Add a microbenchmark in tests if uncertain.

**Deliverable:** we can read/write `.paper.md` files correctly; no UI changes yet.

### Phase 2 — View routing + editor integration (2–3 days)

- [ ] Change `registerExtensions` from `["paper"]` to `["paper.md"]`. Investigate whether Obsidian accepts double extensions here; if not, fall back to pattern matching in a `file-open` handler.
- [ ] Update `PaperView.setViewData` / `getViewData` to use the new serializer. This is the smallest-feasible change: view still holds `PaperDocument`, just parses differently.
- [ ] Implement `file-open` routing: when a `.paper.md` opens in a markdown view and has `paper-default-view: paper` (or missing), swap the leaf to our view.
- [ ] Register `registerMarkdownCodeBlockProcessor("paper", …)` to render a read-only canvas preview inside markdown views (reuse `EmbedRenderer`).
- [ ] Update `src/embed/` post-processor to resolve `![[foo.paper.md]]` and handle the new format (strip markdown wrapper, parse code block, hand to existing renderer).
- [ ] Command: "Create new paper note" — writes a seed `.paper.md` to the current folder and opens in Paper view.
- [ ] Command: "Toggle Paper/Markdown default view."
- [ ] Settings UI: add a note explaining the new format.

**Deliverable:** we can create, open, edit, and embed `.paper.md` files. OCR is not yet wired.

### Phase 3 — Migration command (1 day)

- [ ] Implement `PaperMigrator.ts` with `dryRun(): MigrationReport` and `run(): MigrationReport`.
- [ ] Command palette entry: "Migrate `.paper` files to `.paper.md` (dry run)" and "Migrate `.paper` files to `.paper.md` (run)."
- [ ] Migration modal with summary (file count, estimated size change, list of files that will be touched) before confirming.
- [ ] Tests on synthetic `.paper` inputs (v1, v2, v3) confirming they round-trip via v3 deserializer → v4 serializer without data loss.

**Deliverable:** user can migrate their vault with a single command. Safe by default (dry-run first).

### Phase 4 — OCR infrastructure + MyScript backend (2–3 days)

- [ ] `OcrBackend` interface in `src/ocr/`.
- [ ] `MyScriptBackend.ts` — REST client for `POST /api/v4.0/iink/recognize/text`. Uses Obsidian's `requestUrl` to avoid CORS. Converts our stroke format → MyScript JSON, parses response back.
- [ ] `RasterizeService.ts` — rasterizes a page or line region to a PNG-encoded Blob for image-based backends (reuse `EmbedRenderer` rendering code).
- [ ] `HandwritingOcrBackend.ts` — REST client for handwritingocr.com. Image-based. Reference: [ikmolbo/handwriting-ocr-obsidian-plugin](https://github.com/ikmolbo/handwriting-ocr-obsidian-plugin).
- [ ] Settings UI: backend selection, API key entry, test-connection button, monthly cap field.
- [ ] OCR command: "Recognize handwriting on current page" — runs on the whole page, writes result to transcript.
- [ ] Persist API keys via `this.saveData()` (Obsidian plugin data). Document that this is plaintext storage.

**Deliverable:** on-demand OCR works end-to-end. User can run the command, text lands in the transcript section, frontmatter `paper-ocr.last-run` updates.

### Phase 5 — Incremental re-OCR (2–3 days)

- [ ] `LineClusterer.ts` — clusters strokes into lines, assigns stable IDs.
- [ ] Dirty-line tracker — keyed by line ID, marks lines dirty on stroke add/remove/modify. Lives in `PaperView` state, persisted inside `paper-ocr` code block.
- [ ] Wire auto-OCR on idle (30s debounce after last stroke, only if backend configured).
- [ ] Update `OcrBackend.recognizePage` to accept `dirtyLineIds` and only re-process those lines.
- [ ] Result merger — keeps clean lines' existing OCR output, replaces dirty lines' output, re-emits combined transcript.

**Deliverable:** editing a paragraph in a large document only costs one or two API calls, not a whole-document re-OCR.

### Phase 6 — Polish & UX (1–2 days)

- [ ] Status bar indicator: "OCR: up to date" / "OCR: 3 lines dirty" / "OCR: running…" / "OCR: error (click for details)".
- [ ] Stroke↔word mapping — compute on each OCR result, store in `paper-ocr` code block. No user-facing feature yet, but enables future click-to-navigate.
- [ ] Optional transcript side panel in Paper view (collapsible) for reading OCR output without leaving the editor.
- [ ] Documentation: update `README.md` (if user-facing) with the format change, OCR setup, privacy notes.

**Deliverable:** the feature feels finished.

## Testing Strategy

### Unit tests

- **Serializer round-trip** — `PaperDocument + OcrResult → markdown → PaperDocument + OcrResult` with deep equality.
- **v3 → v4 migration** — hand-crafted v3 JSON inputs → v4 output, deep equality on document content.
- **Frontmatter edge cases** — user-added tags, missing fields, malformed YAML.
- **Transcript regeneration** — synthetic OCR results with unicode, line breaks, empty pages.
- **Line clusterer** — synthetic stroke layouts (neat horizontal lines, tilted, overlapping) with expected line assignments.
- **Dirty-line tracker** — sequences of add/remove/modify with expected dirty sets.
- **OcrBackend mocks** — request payload shape, response parsing, error paths.

### Integration tests (manual, documented checklist)

Before each phase ships to the local vault via `yarn build:copy`:

1. Create a new paper note, write on it, save, close, reopen — renders identically.
2. Embed the note in a markdown file — preview renders.
3. Open the same note in markdown view — code block renders a read-only preview.
4. Toggle default view — closes and reopens in the other mode.
5. Run OCR command — text appears in transcript, frontmatter updates.
6. Edit a single line, save — only that line re-OCRs (check network tab / logs).
7. Search Obsidian for words from the transcript — the paper note appears in results.
8. Rename the paper note — embeds in other files update.
9. Migration dry-run on real `.paper` files — verify report looks correct.
10. Migration real run — verify files converted, originals removed, embeds updated.
11. Mobile sanity check (iPad via iCloud sync) — open, edit, save, OCR runs via `requestUrl`.

## Risks & Mitigations

### High risk

- **View routing fails or flickers.** Obsidian may open the markdown view first, then switch, causing a flash. Mitigation: measure it; if bad, register the view for the exact extension `.paper.md` (if Obsidian supports that) or investigate hiding the markdown editor during the switch with a CSS transition.
- **Migration corrupts a file.** Mitigation: dry-run mode, verification round-trip on each file, keep originals until user opts in to deletion in a second command run.

### Medium risk

- **Markdown parser chokes on 500KB code blocks.** Mitigation: benchmark in Phase 1. If problematic, split compressed JSON across multiple code blocks or externalize to a sidecar file (reluctantly).
- **MyScript rate limits or API shape changes.** Mitigation: thin backend abstraction so swapping services is cheap; monthly-cap safety valve caps costs regardless.
- **User edits transcript manually, gets clobbered on next OCR run.** Mitigation: document the behavior; consider a "user has edited transcript — OCR won't overwrite without confirmation" flag in Phase 6 if it becomes a real issue.
- **Line clustering algorithm misgroups strokes on messy input.** Mitigation: fallback to whole-page re-OCR; expose a setting to disable incremental OCR.

### Low risk

- **Existing uncommitted changes on `main`** (toolbar + preset color separation work) conflict with this refactor. Mitigation: do this work on a dedicated branch from a clean baseline; suggest committing or stashing current toolbar work first.
- **Plugin data file grows** as OCR counters accumulate. Mitigation: bounded counter structure with monthly rollover.

## Open Questions (need decisions before starting)

1. **Backend to ship first in Phase 4?** I'd suggest **Handwriting OCR first**, because you already have an account, the image-based path is simpler to build, and it validates the end-to-end pipeline. Then add MyScript in a follow-up since stroke-based is the quality-optimal path but more code.
2. **Default `paper-default-view` for migrated files?** `paper` (so they continue opening in the drawing editor), or `markdown` (so they default to showing the transcript)? I'd pick `paper`.
3. **Delete original `.paper` files during migration, or leave as backup?** Leave as backup in a first pass; ship a "clean up migrated backups" command in a second pass. You as the only user can run it whenever you feel safe.
4. **Auto-OCR on save, or strictly on-demand?** I'd start on-demand only in Phase 4 (simpler, no debouncing bugs), add auto-OCR in Phase 5 once incremental is in place so it doesn't burn quota.
5. **Where do the uncommitted toolbar changes on `main` fit?** Recommend committing those (or stashing) first so this migration starts from a clean baseline.
6. **Side panel for transcript in Paper view — Phase 6, or skip?** It's nice to have, not required. I'll include it in Phase 6 unless you'd rather cut scope.
